# TRD - Technical Requirements Document: StudyQuest

*Tugas Besar Pemrograman Berorientasi Objek | Revisi 1.1 | Oktober 2026 | Java 17 + JavaFX*

## Status dan acuan revisi

Revisi 1.1, 31 Oktober 2026. Dokumen ini adalah **rencana sebelum implementasi**, bukan laporan fitur yang sudah berjalan. Berkas proyek yang tersedia hanya integrasi awal; tidak dihitung sebagai fitur selesai atau bukti pengujian.

- **Disepakati:** desktop, seluruh fitur F1 sampai F16 tetap ditargetkan, markas 2D bergaya pixel dengan karakter berjalan dan alternatif klik langsung, sub-tugas membantu melemahkan boss, serta streak berdasarkan tugas utama tepat waktu, bukan login harian.
- **Target internal:** selesai pekan 14, diperkirakan 14 sampai 20 Desember 2026 oleh Max. Pekan 15 diperkirakan presentasi/pengumpulan; jadwal resmi belum diverifikasi.
- **Belum ditentukan (O-DB):** kewajiban database/JDBC, penggunaan database, jenis database, dan mekanisme persistensi final. Desktop tidak berarti tanpa database. Serialization maupun SQLite tidak ditetapkan sebagai pilihan inti atau cadangan yang sudah disetujui.
- **Status rincian:** angka balancing, batas input, target performa, dan detail teknis dari draf lama adalah usulan kecuali secara eksplisit disebut disepakati. Jangan menganggap keberadaan tabel atau signature sebagai persetujuan implementasi.
- PRD menjadi acuan kebutuhan dan daftar keputusan terbuka; TRD menguraikan teknis, AFD alur, DBD visual, BSD data, dan IPD pelaksanaan. Konflik harus dibahas dengan Max dan pemilik modul, lalu semua dokumen terkait diperbarui. Agent tidak boleh memilih tafsir sendiri.

## 1. Tujuan dan Ruang Lingkup

Dokumen ini menjelaskan bagaimana StudyQuest dibangun secara teknis: teknologi, arsitektur, struktur kode, kontrak antar modul, alur teknis, penyimpanan data, pengujian, dan cara build. Dokumen ini melengkapi PRD (apa yang dibangun) dan menjadi acuan bersama kelima anggota agar kode yang ditulis terpisah tetap bisa digabung.

## 3. Arsitektur Sistem

Sistem memakai arsitektur berlapis dengan satu pintu masuk (facade) antara UI dan logika permainan.

```
[ UI: Markas 2D + panel JavaFX + MainApp ]
                 |
[ GameController  (Facade) ]
                 |
[ Model: character | quest | item | battle | system ]
                 |
[ DataRepository  ->  adapter persistensi belum dipilih / test double memori ]
```

**Aturan dependensi (wajib dipatuhi):**

1. UI hanya memanggil GameController. UI boleh membaca objek model lewat getter, tetapi tidak boleh mengubah state model secara langsung.
2. Kelas model tidak boleh mengimpor apa pun dari package ui atau javafx.
3. Antar modul hanya memakai kontrak yang disetujui. Bagian 7 adalah calon awal yang perlu dilengkapi untuk sub-tugas, streak, dan markas sebelum coding.
4. Quest dan battle tidak mengenal achievement. Hubungan ke achievement hanya lewat event (pola Observer).
5. Seluruh akses penyimpanan lewat interface DataRepository.

## 5. Desain Komponen per Modul

**Modul 1: Karakter dan Akun.** Character adalah abstract class yang menyimpan level, XP, HP, MP, stat, skill, dan inventory. Method levelUp() adalah template method: ia memanggil applyLevelUpGrowth() yang dioverride Warrior, Mage, dan Archer. Skill adalah interface (pola Strategy) dengan tiga implementasi. AuthService menangani registrasi dan login. Bentuk hasil sesi dan pemuatan GameState harus dikunci bersama pemilik data; jangan menganggap signature integrasi awal sebagai kontrak final.

**Modul 2: Quest.** Quest adalah abstract class dengan calculateReward() dan getType() abstract. Method complete() adalah template method yang menghitung reward lalu menerapkan penalti telat. QuestManager mengelola daftar quest, memberi XP dan gold, dan mempublikasikan event. QuestFactory membuat quest sesuai jenis. Reward adalah value object.

**Modul 3: Inventory dan Shop.** Item (abstract) mengimplementasikan Purchasable. Consumable dan Equipment mewarisi Item dan mengimplementasikan Usable. Inventory menyimpan item, gold, dan equipment aktif. Shop menjual dan membeli item. Kegagalan transaksi dilempar sebagai InsufficientGoldException atau InventoryFullException.

**Modul 4: Boss Battle.** Monster (abstract) memiliki attack(), specialAbility(), dan chooseAction() yang dioverride Slime, Goblin, dan Dragon. MonsterFactory membuat monster dengan stat yang diskalakan. BattleEngine mengatur giliran dengan state PLAYER\_TURN, MONSTER\_TURN, WON, atau LOST.

**Modul 5: Achievement, Statistik, dan Data.** AchievementTracker mengimplementasikan GameEventListener, memperbarui StudyStats, lalu mengevaluasi seluruh Achievement. DataRepository memisahkan cara penyimpanan. GameState adalah akar data. GameController adalah calon facade bersama dengan pemilik belum ditentukan (O-OWNER).

## 8. Alur Teknis Utama

### 8.1 Akun dan markas

UI mengirim permintaan melalui facade ke layanan akun. Setelah autentikasi dan muat data berhasil, akun tanpa karakter diarahkan ke pembuatan karakter, akun lengkap ke markas. Evaluasi keterlambatan dilakukan sebelum menampilkan progres. Kegagalan muat tidak boleh dianggap akun baru atau menyebabkan penimpaan data.

### 8.2 Quest dan streak

Modul Nabil mengelola tugas dan menghasilkan kejadian domain; modul Marcell memperbarui statistik. Tugas utama selesai tepat waktu menambah rentetan, tugas terlambat memutusnya, hari tanpa tugas tidak mengubahnya. Jangan mengikat reset pada status FAILED atau hitungan login. Proses berulang tidak boleh menggandakan reward atau reset; rancangan identitas kejadian dan urutan waktunya dikunci pada O-STREAK.

### 8.3 Sub-tugas dan boss

Modul quest menyediakan progres sub-tugas kepada battle melalui kontrak yang disepakati Nabil dan Deo. Penyelesaian sub-tugas membantu melemahkan boss. Atribut, rumus, snapshot saat battle, dan kapan battle boleh dibuka belum ditentukan (O-BOSS). Usulan: progres mengurangi satu atribut pertahanan/perisai agar implementasi sederhana. Jangan menganggap usulan ini sudah final.

Status penyelesaian akademik dan kemenangan battle perlu dipisahkan dalam kontrak. Usulan guard: kemenangan tidak menandai tugas akademik selesai dan keterlambatan battle tidak membatalkan ketepatan waktu tugas. Distribusi reward quest dan monster ditentukan di satu tempat dengan penanda klaim; jumlah dan waktu klaim menunggu O-BOSS.

### 8.4 Navigasi markas

Arah yang disetujui: berjalan dan alternatif klik langsung. Usulan teknis: satu ruangan, posisi karakter, penghalang persegi sederhana, input empat arah, dan area interaksi objek. WASD/tombol panah untuk berjalan dan E untuk interaksi merupakan usulan binding. Klik dan interaksi keyboard memanggil router yang sama, bukan menggandakan logika domain. Gerakan berhenti saat panel/form menerima fokus dan saat jendela kehilangan fokus.

### 8.5 Simpan dan muat

Aksi domain penting harus memiliki jalur penyimpanan dan pelaporan kegagalan: akun/karakter dibuat, quest/sub-tugas berubah, keterlambatan diproses, reward diklaim, transaksi inventory/shop, hasil battle, dan keluar. Urutan transaksi, rollback, serta kebijakan battle terputus belum final. UI tidak menampilkan Tersimpan sebelum hasil penyimpanan terkonfirmasi. Adapter dipilih setelah O-DB.

## 9. Persistensi Data

**Belum ditentukan (O-DB).** Database tidak diwajibkan atau dilarang oleh dokumen ini. Format file, DDL, driver JDBC, folder data, backup, dan migrasi menunggu klarifikasi rubrik serta keputusan tim.

DataRepository tetap menjadi batas rancangan antara domain dan penyimpanan. InMemoryDataRepository dapat diusulkan sebagai test double sementara, bukan penyimpanan final dan bukan bukti data bertahan setelah aplikasi ditutup. Interface hasil/error, transaksi, dan aturan load dikunci bersama Max dan Marcell sebelum adapter dibangun.

Serializable, serialVersionUID, transient, .dat/.tmp/.bak, dan readObject hanya relevan jika tim kelak memilih Java Serialization. Jangan menerapkannya sebagai kewajiban lintas model saat O-DB masih terbuka. Kebutuhan umum tetap: save/load konsisten, kegagalan eksplisit, dan data lama tidak ditimpa saat pemulihan gagal.

## 10. Penanganan Error dan Validasi

| Situasi | Mekanisme | Perilaku UI |
| --- | --- | --- |
| Gold tidak cukup | InsufficientGoldException | Dialog informasi dengan selisih gold |
| Inventory penuh | InventoryFullException | Dialog informasi dengan kapasitas |
| Input form tidak valid | IllegalArgumentException dari validasi | Pesan di bawah kolom yang salah |
| Username sudah dipakai atau password salah | IllegalArgumentException dengan pesan umum | Pesan di form login atau registrasi |
| Data gagal dimuat/disimpan | Error repository yang disepakati setelah O-DB, tidak terikat format file | Dialog peringatan, data lama tidak ditimpa |
| Aksi tidak valid (MP kurang, quest belum boleh selesai) | IllegalStateException atau nilai balik false | Tombol dinonaktifkan atau pesan singkat |

Aturan umum: model melempar exception, controller menangkap, UI menampilkan. Pesan untuk pengguna berbahasa Indonesia.

## 11. Keamanan

Rancangan berikut perlu dikunci pada O-TECH sebelum implementasi autentikasi:

- Password tidak disimpan sebagai teks asli atau ditulis ke log.
- Gunakan password KDF; usulan tanpa library tambahan ialah PBKDF2WithHmacSHA256 dengan salt acak per akun. Format versi, parameter biaya, panjang salt/hash, dan strategi verifikasi harus ditetapkan serta diuji. SHA-256 langsung tidak dijadikan pilihan final.
- Validasi username dan pesan login umum. Aturan keunikan huruf besar/kecil harus disepakati.
- Setelah O-DB diputuskan: gunakan parameter query untuk database atau pembatasan path dan validasi input untuk berkas. Jangan mengasumsikan backend tertentu sekarang.

## 12. Strategi Pengujian

| Tingkat | Alat | Cakupan |
| --- | --- | --- |
| Unit test | JUnit 5 | Seluruh kelas logika; target minimal 60% |
| Integrasi domain | JUnit 5 + test double memori | Akun, quest, streak, dan boss tanpa UI; tidak membuktikan persistensi final |
| Integrasi UI/data | Skenario UI dan adapter final | Navigasi markas serta save/load setelah O-DB diputuskan |
| Manual | Skenario demo | Seluruh fitur lewat UI |

Daftar uji minimal per modul:

- **Modul 1:** naik level satu dan beberapa kali, HP dan MP pulih penuh, HP tidak negatif, skill ditolak saat MP kurang, damage dasar tiap class, register ganda ditolak, login salah gagal.
- **Modul 2:** reward tiap jenis quest dan tiap kesulitan, streak tugas tepat waktu, penalti telat, transisi keterlambatan sesuai keputusan O-QUEST, guard Weekly sesuai O-QUEST, progres sub-tugas melemahkan boss sesuai O-BOSS.
- **Modul 3:** kapasitas inventory, beli dan jual, gold tidak cukup, equip mengganti item lama, stat kembali setelah unequip, consumable hilang setelah dipakai.
- **Modul 4:** skala stat monster, regenerasi Slime, critical Goblin dengan Random yang diatur, Fire Breath tiap 3 giliran, Dragon enraged, hasil menang dan kalah.
- **Modul 5:** achievement terbuka pada ambang yang benar, streak tugas tepat waktu, hari tanpa tugas netral, dan reset keterlambatan tidak berulang, completion rate, save lalu load menghasilkan state yang sama, data rusak ditangani sesuai adapter final.

## 13. Build, Git, dan Konvensi Kode

**Build.** Maven dengan groupId `com.studyquest`, artifactId `studyquest`, Java 17, dependensi `javafx-controls` dan `javafx-graphics` versi 21.x, serta `junit-jupiter` (scope test). Plugin `javafx-maven-plugin` untuk menjalankan aplikasi.

**Git.** Cabang `main` selalu bisa dibuild. Setiap anggota bekerja di cabang `feature/<modul>-<fitur>`. Penggabungan lewat pull request dengan minimal satu reviewer dari anggota lain dan semua test lulus.

**Konvensi kode.**

- Nama kelas PascalCase, method dan variabel camelCase, konstanta UPPER\_SNAKE\_CASE.
- Atribut selalu private atau protected; akses lewat getter dan setter.
- Javadoc wajib untuk method pada kontrak antar modul.
- Tidak ada angka ajaib: rumus dan nilai aturan bisnis ditempatkan sebagai konstanta bernama.
- Satu file satu kelas publik; indentasi 4 spasi.

## 14. Performa dan Batasan Teknis

Target demo: i7 generasi 13/RTX 4050 atau i5 generasi 12/RTX 3050, berdasarkan informasi Max. OS, RAM, resolusi, dan model CPU lengkap belum diketahui. Jadikan alternatif i5/RTX 3050 target awal pengujian, bukan spesifikasi minimum terverifikasi.

Uji respons input, kelancaran gerak, pemuatan aset, penggunaan memori, dan durasi save/load pada perangkat nyata. Target angka pada PRD masih usulan. Jangan mengklaim serialization selesai dalam waktu tertentu tanpa pengukuran atau bergantung pada GPU RTX.

Usulan batas implementasi: satu markas 2D, animasi sederhana, battle bergiliran, tanpa dunia luas atau pencarian jalur otomatis. Render dan input dipisahkan dari operasi I/O agar antarmuka tidak membeku. Pilihan thread dan snapshot state harus diuji bersama strategi penyimpanan.

## 15. Cara Menjalankan

Bagian ini adalah rencana validasi, bukan bukti aplikasi sudah dapat dimainkan.

1. Kunci versi JDK, JavaFX, Maven, dan konfigurasi test pada fase fondasi.
2. Setelah implementasi tersedia, jalankan `mvn clean test` dan catat hasil nyata.
3. Setelah entry point GUI tersedia, verifikasi `mvn javafx:run` membuka aplikasi yang dimaksud.
4. Uji save/load menggunakan adapter final setelah O-DB selesai.
5. Uji distribusi pada laptop demo; installer atau runtime bundel belum dipilih (O-DEVICE).

Berkas integrasi awal tidak dihitung sebagai keberhasilan langkah-langkah tersebut.
