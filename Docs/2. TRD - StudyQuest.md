# TRD - Technical Requirements Document: StudyQuest

*Tugas Besar Pemrograman Berorientasi Objek | Revisi 1.3 | November 2026 | Java 27 + JavaFX*

## Status dan acuan revisi

Revisi 1.3, 12 November 2026. Dokumen ini adalah **rencana sebelum implementasi**. Branch `main` baru berisi struktur package kosong, `pom.xml`, `README.md`, dan `Docs/`; belum ada fitur yang dihitung selesai atau teruji.

- **Disepakati:** aplikasi desktop JavaFX; seluruh fitur F1 sampai F16 wajib selesai; markas 2D bergaya pixel satu ruangan dengan karakter berjalan dan alternatif klik; sub-tugas melemahkan boss; streak dihitung dari tugas yang selesai tepat waktu, bukan login harian. Daftar keputusan yang dikunci ada di PRD §14.
- **Penyimpanan dikunci (O-DB, 11 November 2026):** dosen tidak mewajibkan database, jadi data disimpan lokal memakai Java Serialization: satu berkas `.dat` per akun, ditulis lewat berkas `.tmp` lalu menggantikan berkas utama, dengan satu cadangan `.bak`. Tidak memakai JDBC, SQL, atau library tambahan. Rincian teknis ada di TRD §9 dan BSD §6.
- **Target internal:** selesai pekan 14, perkiraan 14 sampai 20 Desember 2026. Pekan 15 diperkirakan presentasi/pengumpulan; jadwal resmi belum diverifikasi.
- **Angka balancing:** nilai di PRD §8 dan BSD §9 dipakai sebagai nilai awal saat coding, ditulis sebagai konstanta bernama, dan boleh disetel setelah uji main atas persetujuan pemilik modul. Aturan alur (kapan streak pecah, kapan battle boleh dimulai, dan sejenisnya) tidak diubah tanpa persetujuan Max.
- **Persetujuan Max, 12 November 2026:** aturan Daily dan klaim hadiah Boss dikunci; pelemahan boss hanya HP (tanpa defense, ATK tetap); Max memegang `theme.css` serta pemilihan warna/aset; password memakai PBKDF2 sesuai TRD §11. Tanggal per fase dan penggambaran ulang diagram tidak menjadi syarat coding.
- **Per anggota:** setiap anggota dan agent-nya mulai dari `Docs/7. Panduan Role per Modul - StudyQuest.md` pada bagian modulnya, lalu membaca bagian dokumen lain yang dirujuk di sana.
- **Urutan acuan saat konflik:** PRD §14, lalu PRD, TRD, BSD, AFD, DBD, IPD. Konflik dilaporkan ke Max dan pemilik modul, lalu semua dokumen terkait diperbarui. Agent tidak memilih tafsir sendiri dan tidak menutup keputusan terbuka.

## 3. Arsitektur Sistem

Sistem memakai arsitektur berlapis dengan satu pintu masuk (facade) antara UI dan logika permainan.

```
[ UI: Markas 2D + panel JavaFX + MainApp ]
                 |
[ GameController  (Facade) ]
                 |
[ Model: character | quest | item | battle | system ]
                 |
[ DataRepository  ->  FileDataRepository (.dat lokal) | InMemoryDataRepository (test) ]
```

**Aturan dependensi (wajib dipatuhi):**

1. UI hanya memanggil GameController. UI boleh membaca objek model lewat getter, tetapi tidak boleh mengubah state model secara langsung.
2. Kelas model tidak boleh mengimpor apa pun dari package ui atau javafx.
3. Antar modul hanya memakai kontrak yang disetujui. Bagian 7 adalah calon awal yang perlu dilengkapi untuk sub-tugas, streak, dan markas sebelum coding.
4. Quest dan battle tidak mengenal achievement. Hubungan ke achievement hanya lewat event (pola Observer).
5. Seluruh akses penyimpanan lewat interface DataRepository.

## 5. Desain Komponen per Modul

**Modul 1: Karakter dan Akun.** Character adalah abstract class yang menyimpan level, XP, HP, MP, stat, skill, dan inventory. Method levelUp() adalah template method: ia memanggil applyLevelUpGrowth() yang dioverride Warrior, Mage, dan Archer. Skill adalah interface (pola Strategy) dengan tiga implementasi. AuthService menangani registrasi dan login dan menghasilkan sesi `GameState` (sesuai proposal §3.3.2) dengan memanggil `DataRepository`.

**Modul 2: Quest.** Quest adalah abstract class dengan calculateReward() dan getType() abstract. Method complete() adalah template method yang menghitung reward lalu menerapkan penalti telat. QuestManager mengelola daftar quest, memberi XP dan gold, dan mempublikasikan event. QuestFactory membuat quest sesuai jenis. Reward adalah value object.

**Modul 3: Inventory dan Shop.** Item (abstract) mengimplementasikan Purchasable. Consumable dan Equipment mewarisi Item dan mengimplementasikan Usable. Inventory menyimpan item, gold, dan equipment aktif. Shop menjual dan membeli item. Kegagalan transaksi dilempar sebagai InsufficientGoldException atau InventoryFullException.

**Modul 4: Boss Battle.** Monster (abstract) memiliki attack(), specialAbility(), dan chooseAction() yang dioverride Slime, Goblin, dan Dragon. MonsterFactory membuat monster dengan stat yang diskalakan. BattleEngine mengatur giliran dengan state PLAYER\_TURN, MONSTER\_TURN, WON, atau LOST.

**Modul 5: Achievement, Statistik, dan Data.** AchievementTracker mengimplementasikan GameEventListener, memperbarui StudyStats, lalu mengevaluasi seluruh Achievement. DataRepository memisahkan cara penyimpanan; FileDataRepository menulis berkas `.dat`. GameState adalah akar data. Marcell memegang kerangka GameController; method per modul ditulis pemilik modul.

## 8. Alur Teknis Utama

### 8.1 Akun dan markas

UI memanggil `GameController.login`. AuthService memeriksa `exists`, memuat `GameState`, lalu memverifikasi password. GameController memanggil `GameState.rewire()` dan `processOverdue()` sebelum menampilkan progres. Akun tanpa karakter diarahkan ke S03, akun lengkap ke markas. Kegagalan muat tidak dianggap akun baru dan tidak menimpa data.

### 8.2 Quest dan streak

Modul Nabil mengelola tugas dan mengirim `GameEvent`; modul Marcell memperbarui statistik. Deadline bertipe `LocalDate` dan memakai zona waktu sistem. Quest dianggap telat jika `LocalDate.now()` sudah melewati deadline.

- Selesai pada atau sebelum deadline: event `QUEST_COMPLETED` dengan `onTime = true`, streak +1.
- `checkOverdue` menemukan Weekly/Boss belum selesai setelah deadline: event `QUEST_OVERDUE` satu kali (flag `overduePenaltyApplied`), streak menjadi 0.
- Selesai 1 sampai 3 hari setelah deadline: reward x 0,5, event `QUEST_COMPLETED` dengan `onTime = false`, streak tidak bertambah.
- Lebih dari 3 hari setelah deadline: status FAILED, `loseXP(10)`, event `QUEST_FAILED` satu kali.
- Mengubah deadline atau menghapus quest tidak menghapus keterlambatan yang sudah tercatat. Hari tanpa quest tidak mengubah streak. Daily bisa selesai sekali per hari; kesempatan reward yang terlewat hangus tanpa penalti XP atau pemutusan streak (O-DAILY). Saat hari berganti, Daily kembali ACTIVE dengan deadline hari ini; `lastCompletedDate` mencegah klaim dua kali pada hari yang sama. Daily tidak masuk jalur OVERDUE/FAILED Weekly dan Boss.

### 8.3 Sub-tugas dan boss

`GameController.startBossBattle(questId)` mengambil `BossQuest.getSubTaskProgress()` (0 sampai 1) saat battle dimulai, lalu memanggil `MonsterFactory.createWeakened(type, level, progres)`. Pelemahan maksimal 40%; O-WEAKEN dikunci: HP maks dan HP awal boss menjadi HP dasar dikali `1 - 0,4 x progres` (PRD §14). Monster tidak memakai defense dan ATK tidak ikut dikurangi. Perubahan sub-tugas selama battle tidak memengaruhi battle yang sedang berjalan. Battle boleh dimulai kapan saja, termasuk saat progres 0.

Status akademik dan battle terpisah:

- Tombol Tandai Tugas Selesai memanggil `completeQuest`, yang memanggil `markAcademicCompleted()` dan memberi reward akademik (dasar x 4, dipotong jika telat). Syarat semua sub-tugas dicentang mengikuti O-CLAIM yang dikunci.
- Battle WON memanggil `recordBossDefeated(questId)`. Reward monster dan item drop diambil lewat `claimBossReward(questId)` satu kali (`battleRewardClaimed`). Jika tas penuh, klaim ditolak utuh dengan InventoryFullException dan bisa diulang (O-CLAIM dikunci).
- Battle LOST atau `surrender()`: `setHpToOne()`, item yang sudah dipakai tetap hilang, tanpa reward, boss boleh dilawan ulang.
- Menutup aplikasi saat battle diperlakukan sama dengan menyerah sebelum data disimpan. `BattleEngine` tidak disimpan.

### 8.4 Navigasi markas

Arah yang disetujui: berjalan dan alternatif klik langsung. Usulan teknis: satu ruangan, posisi karakter, penghalang persegi sederhana, input empat arah, dan area interaksi objek. WASD/tombol panah untuk berjalan dan E untuk interaksi merupakan usulan binding. Klik dan interaksi keyboard memanggil router yang sama, bukan menggandakan logika domain. Gerakan berhenti saat panel/form menerima fokus dan saat jendela kehilangan fokus.

### 8.5 Simpan dan muat

`saveNow()` dipanggil setelah aksi berikut berhasil: akun/karakter dibuat, quest atau sub-tugas berubah, keterlambatan diproses, reward diklaim, transaksi inventory/shop, hasil battle, dan saat jendela ditutup. Validasi dilakukan sebelum state diubah supaya kegagalan tidak meninggalkan perubahan setengah jalan. UI menampilkan Tersimpan hanya setelah `save` selesai tanpa exception.

## 9. Persistensi Data

**Dikunci (O-DB, 11 November 2026):** dosen tidak mewajibkan database. Data disimpan lokal dengan Java Serialization, tanpa JDBC dan tanpa library tambahan.

| Aspek | Ketentuan |
| --- | --- |
| Lokasi | `System.getProperty("user.home")/.studyquest/saves/`; konstruktor `FileDataRepository(Path baseDir)` agar test memakai folder sementara |
| Nama berkas | `<username huruf kecil>.dat`; username sudah divalidasi `[A-Za-z0-9_]{3,20}` sehingga aman menjadi nama berkas |
| Isi | Satu objek `GameState` per akun |
| Simpan | Tulis ke `<u>.dat.tmp`, salin `<u>.dat` lama menjadi `<u>.dat.bak` jika ada, lalu `Files.move(tmp, dat, REPLACE_EXISTING, ATOMIC_MOVE)`; jika ATOMIC_MOVE tidak didukung, ulangi tanpa ATOMIC_MOVE |
| Muat | Baca `<u>.dat`; jika gagal, coba `<u>.dat.bak` dan beri tahu UI bahwa cadangan dipakai; jika keduanya gagal, lempar `IOException` tanpa menimpa berkas apa pun |
| Kelas yang disimpan | Semua kelas di dalam `GameState` mengimplementasikan `Serializable` dengan `private static final long serialVersionUID = 1L` |
| Tidak disimpan | `QuestManager.listeners` dan katalog `Shop` bertanda `transient`, dipasang ulang lewat `GameState.rewire()`; `BattleEngine`, `BattleLog`, kelas UI, dan `GameController` tidak masuk `GameState` |
| Kompatibilitas | Selama pengembangan, berkas save adalah data uji yang boleh dibuang. Mulai fase P4, field kelas yang disimpan dibekukan; perubahan setelahnya wajib disertai rencana migrasi |

`InMemoryDataRepository` hanya untuk test dan tidak membuktikan data bertahan setelah aplikasi ditutup.

## 11. Keamanan

Parameter berikut disetujui Max untuk Modul 1 (O-TECH, 12 November 2026):

- Algoritma `PBKDF2WithHmacSHA256` lewat `javax.crypto.SecretKeyFactory`, salt 16 byte dari `SecureRandom`, 120.000 iterasi, panjang hasil 256 bit.
- Format tersimpan di `User.passwordHash`: `pbkdf2-sha256$120000$<salt Base64>$<hash Base64>`. Format berversi ini memungkinkan iterasi dinaikkan tanpa merusak akun lama.
- Verifikasi memakai `MessageDigest.isEqual` agar perbandingan tidak bocor lewat waktu.
- Password tidak disimpan sebagai teks asli dan tidak ditulis ke log. Pesan login salah selalu umum.
- Username dibandingkan tanpa membedakan huruf besar/kecil dan disimpan dalam huruf kecil (dikunci).
- Nama berkas hanya berasal dari username yang lolos validasi, jadi tidak ada path dari input mentah.
- Akun hanya untuk penggunaan lokal; email, OTP, dan reset password tidak termasuk cakupan.

## 12. Strategi Pengujian

| Tingkat | Alat | Cakupan |
| --- | --- | --- |
| Unit test | JUnit 5 | Seluruh kelas logika; target minimal 60% |
| Integrasi domain | JUnit 5 + test double memori | Akun, quest, streak, dan boss tanpa UI; tidak membuktikan persistensi final |
| Integrasi data | JUnit 5 + `@TempDir` + FileDataRepository | Save lalu load menghasilkan state sama, berkas rusak memakai `.bak`, berkas rusak tanpa cadangan tidak ditimpa |
| Manual | Skenario demo | Seluruh fitur lewat UI |

Daftar uji minimal per modul:

- **Modul 1:** naik level satu dan beberapa kali, HP dan MP pulih penuh, HP tidak negatif, skill ditolak saat MP kurang, damage dasar tiap class, register ganda ditolak, login salah gagal.
- **Modul 2:** reward tiap jenis quest dan tiap kesulitan, reward 50% saat telat 1 sampai 3 hari, FAILED dan XP -10 setelah 3 hari, `checkOverdue` dua kali tidak menggandakan penalti, Weekly tidak bisa selesai sebelum semua sub-tugas dicentang, Daily bisa selesai sekali per hari, progres sub-tugas 0 sampai 1.
- **Modul 3:** kapasitas 20 dan perluasan sampai 25, beli dan jual, gold tidak cukup, equip mengganti item lama, stat kembali setelah unequip, consumable hilang setelah dipakai, upgrade sampai +5 lalu ditolak, upgrade item terpasang memperbarui stat karakter.
- **Modul 4:** skala stat monster, pelemahan HP pada 0%, 50%, dan 100% progres (maksimal 40%) dengan ATK tetap, regenerasi Slime, critical Goblin dengan Random yang diatur, Fire Breath tiap 3 giliran, Dragon enraged, Defend memotong damage 50%, kalah dan menyerah membuat HP 1.
- **Modul 5:** achievement terbuka pada ambang yang benar, streak tugas tepat waktu, hari tanpa tugas netral, reset keterlambatan tidak berulang, completion rate, save lalu load menghasilkan state sama, berkas rusak memakai `.bak`, berkas rusak tanpa cadangan melempar IOException tanpa menimpa.

**Build.** Maven dengan groupId `com.studyquest`, artifactId `studyquest`, Java 27, dependensi `javafx-controls` dan `javafx-fxml` 21.0.2, serta `junit-jupiter-api`/`junit-jupiter-engine` 5.10.2 (scope test). Plugin `javafx-maven-plugin` 0.0.8 dengan main class `com.studyquest.MainApp`.

**Git.** Cabang `main` selalu bisa dibuild. Setiap anggota bekerja di cabang `feature/<modul>-<fitur>`. Penggabungan lewat pull request dengan minimal satu reviewer dari anggota lain dan semua test lulus.

**Konvensi kode.**

- Nama kelas PascalCase, method dan variabel camelCase, konstanta UPPER\_SNAKE\_CASE.
- Atribut selalu private atau protected; akses lewat getter dan setter.
- Javadoc wajib untuk method pada kontrak antar modul.
- Tidak ada angka ajaib: rumus dan nilai aturan bisnis ditempatkan sebagai konstanta bernama.
- Satu file satu kelas publik; indentasi 4 spasi.

## 14. Performa dan Batasan Teknis

Target demo: i7 generasi 13/RTX 4050 atau i5 generasi 12/RTX 3050, berdasarkan informasi Max. OS, RAM, resolusi, dan model CPU lengkap belum diketahui. Jadikan alternatif i5/RTX 3050 target awal pengujian, bukan spesifikasi minimum terverifikasi.

Uji respons input, kelancaran gerak, pemuatan aset, penggunaan memori, dan durasi save/load pada perangkat nyata. Target angka pada PRD masih usulan. Jangan mengklaim serialization selesai dalam waktu tertentu tanpa pengukuran atau bergantung pada GPU RTX.

Usulan batas implementasi: satu markas 2D, animasi sederhana, battle bergiliran, tanpa dunia luas atau pencarian jalur otomatis. Render dan input dipisahkan dari operasi I/O agar antarmuka tidak membeku. Pilihan thread dan snapshot state harus diuji bersama strategi penyimpanan.

## 15. Cara Menjalankan

Bagian ini adalah rencana validasi, bukan bukti aplikasi sudah dapat dimainkan.

1. Kunci versi JDK, JavaFX, Maven, dan konfigurasi test pada fase fondasi.
2. Setelah implementasi tersedia, jalankan `mvn clean test` dan catat hasil nyata.
3. Setelah entry point GUI tersedia, verifikasi `mvn javafx:run` membuka aplikasi yang dimaksud.
4. Uji save/load dengan FileDataRepository: tutup aplikasi, buka lagi, login, dan pastikan progres sama.
5. Uji distribusi pada laptop demo; installer atau runtime bundel belum dipilih (O-DEVICE).

Berkas integrasi awal tidak dihitung sebagai keberhasilan langkah-langkah tersebut.
