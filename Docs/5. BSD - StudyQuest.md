# BSD - Backend Schema Documentation: StudyQuest

*Tugas Besar Pemrograman Berorientasi Objek | Revisi 1.1 | Oktober 2026*

## Status dan acuan revisi

Revisi 1.1, 31 Oktober 2026. Dokumen ini adalah **rencana sebelum implementasi**, bukan laporan fitur yang sudah berjalan. Berkas proyek yang tersedia hanya integrasi awal; tidak dihitung sebagai fitur selesai atau bukti pengujian.

- **Disepakati:** desktop, seluruh fitur F1 sampai F16 tetap ditargetkan, markas 2D bergaya pixel dengan karakter berjalan dan alternatif klik langsung, sub-tugas membantu melemahkan boss, serta streak berdasarkan tugas utama tepat waktu, bukan login harian.
- **Target internal:** selesai pekan 14, diperkirakan 14 sampai 20 Desember 2026 oleh Max. Pekan 15 diperkirakan presentasi/pengumpulan; jadwal resmi belum diverifikasi.
- **Belum ditentukan (O-DB):** kewajiban database/JDBC, penggunaan database, jenis database, dan mekanisme persistensi final. Desktop tidak berarti tanpa database. Serialization maupun SQLite tidak ditetapkan sebagai pilihan inti atau cadangan yang sudah disetujui.
- **Status rincian:** angka balancing, batas input, target performa, dan detail teknis dari draf lama adalah usulan kecuali secara eksplisit disebut disepakati. Jangan menganggap keberadaan tabel atau signature sebagai persetujuan implementasi.
- PRD menjadi acuan kebutuhan dan daftar keputusan terbuka; TRD menguraikan teknis, AFD alur, DBD visual, BSD data, dan IPD pelaksanaan. Konflik harus dibahas dengan Max dan pemilik modul, lalu semua dokumen terkait diperbarui. Agent tidak boleh memilih tafsir sendiri.

## 1. Ringkasan dan Catatan Penting

Backend pada dokumen ini berarti model domain dan kontrak pengelolaan data aplikasi desktop, bukan keputusan membangun web/server. **Database dan mekanisme persistensi belum ditentukan (O-DB).** Kewajiban database/JDBC dari dosen belum diketahui lengkap.

Dokumen mendefinisikan kebutuhan data secara logis sebelum implementasi. GameState adalah calon agregat sesi dari integrasi awal, bukan kewajiban menyimpan seluruh objek menjadi satu file. Serialization, SQLite, tabel fisik, format berkas, dan adapter produksi belum dipilih. DDL opsional draf lama ditarik dari acuan aktif agar tidak dianggap keputusan tim.

## 2. Prinsip Persistensi

- Data tiap akun harus terisolasi secara logis; tidak mengasumsikan satu file per pengguna.
- Akses simpan/muat melalui batas DataRepository yang kontraknya perlu disepakati.
- Operasi lintas entitas harus konsisten: item/gold, quest/reward, sub-tugas/pelemahan, serta streak/riwayat.
- Kegagalan simpan atau muat dilaporkan; data lama tidak ditimpa diam-diam.
- Data turunan, listener, dan state tampilan tidak otomatis dipersistensikan.
- Kebutuhan backup, pemulihan, versi skema, dan kompatibilitas harus dipenuhi oleh rancangan final setelah O-DB, bukan dianggap sudah tersedia.

## 5. Relasi Antar Entitas

- GameState memiliki satu User, satu QuestManager, satu Shop, satu AchievementTracker, dan satu StudyStats (komposisi).
- User memiliki nol atau satu Character; Character memiliki tepat satu Inventory (komposisi) dan satu atau lebih Skill.
- Inventory menghimpun nol atau banyak Item dan paling banyak tiga Equipment terpasang.
- QuestManager menghimpun nol atau banyak Quest.
- AchievementTracker menghimpun banyak Achievement dan merujuk satu StudyStats.
- Reward merujuk nol atau satu Item (hanya saat berjalan, tidak disimpan).

## 6. Struktur File

**Belum ditentukan (O-DB).** Jangan membuat kontrak `.dat`, `.tmp`, `.bak`, lokasi database, maupun direktori data produksi sebagai keputusan final.

Setelah pilihan persistensi disetujui, isi bagian ini dengan lokasi data per OS, struktur file atau tabel, aturan kepemilikan akun, transaksi, backup, dan perlindungan data pengguna. File data pengguna tidak dimasukkan ke Git; aturan ignore final mengikuti format yang dipilih.

## 7. Operasi Data

Calon operasi: simpan state/perubahan, muat akun dan progres, periksa keberadaan identitas, serta transaksi reward/inventory. `save(GameState)`, `load(String)`, dan `exists(String)` pada integrasi awal hanya bahan kontrak. Bentuk error, transaksi, dan hasil sukses perlu disepakati (O-TECH/O-DB).

Penghapusan akun belum menjadi kebutuhan yang disepakati; `delete(username)` pada draf lama bukan kontrak wajib. Hapus quest tetap fitur F5 dan membutuhkan aturan riwayat streak. Tidak ada operasi data yang boleh diam-diam memilih backend atau menghapus data lama untuk mengatasi ketidakcocokan.

## 8. Aturan Integritas (Invariants)

1. Username unik; nama file diturunkan dari username yang sudah divalidasi.
2. `hp` tidak pernah di bawah 0 atau di atas `maxHp`; `mp` berlaku sama.
3. `gold` dan harga tidak pernah negatif; pembelian atomik: gold berkurang dan item masuk bersama-sama atau tidak sama sekali.
4. Ukuran `Inventory.items` tidak melebihi `capacity`.
5. Satu slot equipment hanya berisi satu item; mengganti item mengembalikan item lama ke `items`.
6. Id quest unik dan `nextId` selalu bertambah.
7. Siklus tugas, recurrence, dan FAILED menunggu O-QUEST; keterlambatan tidak disamakan dengan kegagalan battle.
8. Penyelesaian akademik, sub-tugas, hasil battle, dan reward memiliki tanggung jawab terpisah. Aturan Weekly/Boss menunggu O-QUEST/O-BOSS; jangan memakai bossDefeated sebagai satu-satunya bukti tugas selesai.
9. Achievement yang sudah terbuka tidak dikunci kembali.
10. `StudyStats.longestStreak` tidak pernah turun.

## 10. Skema Fisik: Belum Ditentukan

**Belum ditentukan (O-DB).** Tidak ada DDL yang disahkan. Database bukan fitur tambahan yang hanya dikerjakan jika sempat; kebutuhan dan pemilihannya menunggu rubrik dosen serta keputusan tim.

Saat O-DB diputuskan, turunkan model logis menjadi skema fisik sesuai backend yang dipilih. Review identitas instance item versus kode katalog, relasi sub-tugas Boss, status akademik/battle, deduplikasi kejadian streak, penanda klaim reward, dan konsistensi transaksi. Jangan menjalankan DDL lama sebagai baseline tanpa review tersebut.

## 11. Versi Skema dan Migrasi

Strategi versi dan migrasi belum ditentukan sampai O-DB selesai. Nomor serialVersionUID bukan strategi universal dan tidak boleh diterapkan sebagai kewajiban database.

Rancangan final harus menjelaskan versi data, deteksi format tidak kompatibel, tindakan pemulihan, dan test data lama. Jangan menyuruh anggota menghapus data pengguna sebagai prosedur migrasi. Data uji yang dapat dibuang harus terpisah dan jelas berlabel.

## 12. Pencadangan dan Pemulihan

Kebutuhan: data tidak hilang karena penimpaan saat save/load gagal; pengguna mendapat status yang benar dan cara pemulihan yang jelas. Mekanisme backup/restore, jadwal, format, dan kebijakan saat battle terputus masih O-DB/O-BOSS.

Setelah diputuskan, uji operasi normal, data rusak, izin tulis ditolak, proses terputus, dan pemulihan. Tidak ada klaim mekanisme `.bak` atau recovery sudah berjalan pada tahap perencanaan ini.
