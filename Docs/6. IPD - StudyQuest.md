# IPD - Implementation Plan Documentation: StudyQuest

*Tugas Besar Pemrograman Berorientasi Objek | Revisi 1.1 | Oktober 2026 | Tim 5 anggota | Target internal pekan 14*

## Status dan acuan revisi

Revisi 1.1, 31 Oktober 2026. Dokumen ini adalah **rencana sebelum implementasi**, bukan laporan fitur yang sudah berjalan. Berkas proyek yang tersedia hanya integrasi awal; tidak dihitung sebagai fitur selesai atau bukti pengujian.

- **Disepakati:** desktop, seluruh fitur F1 sampai F16 tetap ditargetkan, markas 2D bergaya pixel dengan karakter berjalan dan alternatif klik langsung, sub-tugas membantu melemahkan boss, serta streak berdasarkan tugas utama tepat waktu, bukan login harian.
- **Target internal:** selesai pekan 14, diperkirakan 14 sampai 20 Desember 2026 oleh Max. Pekan 15 diperkirakan presentasi/pengumpulan; jadwal resmi belum diverifikasi.
- **Belum ditentukan (O-DB):** kewajiban database/JDBC, penggunaan database, jenis database, dan mekanisme persistensi final. Desktop tidak berarti tanpa database. Serialization maupun SQLite tidak ditetapkan sebagai pilihan inti atau cadangan yang sudah disetujui.
- **Status rincian:** angka balancing, batas input, target performa, dan detail teknis dari draf lama adalah usulan kecuali secara eksplisit disebut disepakati. Jangan menganggap keberadaan tabel atau signature sebagai persetujuan implementasi.
- PRD menjadi acuan kebutuhan dan daftar keputusan terbuka; TRD menguraikan teknis, AFD alur, DBD visual, BSD data, dan IPD pelaksanaan. Konflik harus dibahas dengan Max dan pemilik modul, lalu semua dokumen terkait diperbarui. Agent tidak boleh memilih tafsir sendiri.

## 1. Ringkasan dan Strategi

Tim belum memulai implementasi fitur; yang tersedia hanya integrasi awal. Jangan menghitungnya sebagai progres selesai. Dokumen ini menyelaraskan pekerjaan anggota dan agent sebelum coding.

1. Sepakati kebutuhan, status keputusan, kontrak, dan kepemilikan bersama.
2. Buat fondasi dan uji kontrak, bukan langsung mempercantik semua layar.
3. Buktikan satu alur terhubung: markas, navigasi, quest/sub-tugas, pelemahan boss, dan simpan/muat. Test double memori boleh membantu pengujian awal tetapi tidak membuktikan persistensi final.
4. Lengkapi seluruh fitur, integrasikan bertahap, lalu perbaiki visual dan masalah penggunaan.
5. Siapkan pengujian dan demo sebelum target akhir pekan 14.

Seluruh fitur wajib dipertahankan. Kompleksitas visual dan mekanisme tambahan dibatasi untuk menjaga kelayakan. Tidak ada jaminan selesai sebelum kapasitas anggota dan keputusan penting dipastikan.

## 5. Ketergantungan dan Jalur Kritis

- UI memerlukan router/facade dan kontrak domain, bukan seluruh detail domain selesai sekaligus.
- Quest memerlukan kontrak karakter/inventory dan kejadian statistik.
- Pelemahan boss memerlukan kesepakatan progres sub-tugas antara Nabil dan Deo.
- Streak memerlukan urutan kejadian dan deadline antara Nabil dan Marcell.
- Adapter persistensi dan distribusi menunggu O-DB serta O-DEVICE.
- Seluruh pekerjaan bersama menunggu pemilik SH-01/SH-02.

Jalur risiko: keputusan penghambat, kontrak, alur terhubung, kelengkapan fitur, persistensi final, pengujian perangkat, lalu demo. Jadwal rinci belum boleh dinyatakan realistis sebelum kapasitas dan dependensi dipetakan.

## 6. Alur Kerja Git dan Review

- Cabang `main` selalu bisa di-build dan seluruh test lulus. Tidak ada commit langsung ke `main`.
- Nama cabang: `feature/<modul>-<deskripsi>` (contoh `feature/quest-weekly`), perbaikan bug `fix/<deskripsi>`.
- Pesan commit singkat dan jelas dalam bentuk perintah: `Tambah DailyQuest.calculateReward`.
- Setiap pull request: ukuran kecil (idealnya di bawah 400 baris), satu reviewer dari anggota lain, test lulus, dan deskripsi mengacu ke ID tugas (misalnya A2-03).
- Penggabungan sering (minimal sekali per minggu) agar konflik tetap kecil.
- Penanggung jawab rilis/tag mengikuti O-OWNER, tidak otomatis Anggota 5.
- Perubahan pada kontrak antar modul wajib dibahas di pertemuan dan dicatat pada TRD.

## 9. Komunikasi dan Ritme Kerja

- **Pertemuan sinkron:** dua kali seminggu, 30 menit (awal minggu untuk rencana, akhir minggu untuk demo kemajuan).
- **Chat harian:** laporkan hambatan segera, jangan menunggu pertemuan.
- **Papan tugas:** daftar tugas pada bagian 4 dipindahkan ke papan sederhana (Kanban: To Do, Doing, Review, Done).
- **Catatan keputusan:** perubahan kontrak, aturan permainan, atau desain dicatat singkat di dokumen bersama.

## 10. Daftar Risiko

| Risiko | Mitigasi perencanaan |
| --- | --- |
| Kapasitas belum diketahui | Minta estimasi nyata, tetapkan tanggal per tugas, jangan menjanjikan selesai berdasarkan tabel contoh |
| O-DB terlambat | Klarifikasi rubrik; uji domain melalui abstraction, jangan membangun adapter asumsi |
| Markas menjadi proyek gim besar | Usulkan satu ruangan, penghalang sederhana, animasi singkat, tanpa dunia luas/pathfinding |
| Beban bersama menumpuk pada Marcell | Tetapkan SH-01/SH-02 terpisah dari modul data dan hitung kapasitasnya |
| Agent membuat keputusan sendiri | Gunakan status keputusan, review lintas modul, serta matriks F/test/owner |
| Streak/reward tidak konsisten | Selesaikan kontrak waktu, klaim sekali dan progres sub-tugas sebelum integrasi |
| Data hilang | Rancang transaksi/recovery setelah O-DB; jangan menghapus data pengguna untuk mengatasi bug |
| Performa demo tidak sesuai | Uji pada i5 generasi 12/RTX 3050 atau alternatif i7 generasi 13/RTX 4050; OS/RAM masih terbuka |
| Aset terlalu berat dikerjakan | Batasi variasi visual, pilih aset berlisensi setelah persetujuan, prioritaskan fungsi |

## 11. Penanganan Risiko Jadwal Tanpa Pemangkasan Sepihak

Seluruh fitur wajib tetap dipertahankan. Grafik statistik, tiga jenis achievement, perilaku Dragon, pengelolaan quest, Defend, dan Use Item tidak boleh dihapus sebagai keputusan sepihak.

Saat jadwal terancam:
1. Hentikan penambahan fitur atau dekorasi yang tidak disepakati.
2. Sederhanakan detail animasi, jumlah variasi aset, dan teknik internal tanpa menghilangkan perilaku wajib.
3. Pecah tugas bersama dan alihkan pekerjaan melalui kesepakatan pemilik; perbarui estimasi.
4. Selesaikan keputusan penghambat dan integrasi lebih awal.
5. Laporkan selisih kapasitas terhadap target kepada Max. Perubahan scope atau tenggat harus menjadi keputusan eksplisit, bukan penyuntingan PRD diam-diam.

Gerak karakter dengan alternatif klik tetap arah yang disetujui; jangan menghapusnya tanpa pembahasan kelayakan.

## 12. Definition of Done

**Per kelas atau tugas:** sesuai class diagram (atribut dan method), access modifier benar, memiliki unit test yang lulus, Javadoc pada method kontrak, kontrak persistensi sesuai keputusan O-DB, dan sudah di-merge lewat pull request yang direview.

**Per fitur:** kriteria penerimaan pada PRD terpenuhi lewat UI dan dapat didemonstrasikan.

**Per rilis:** semua fitur F1 sampai F16 lulus, skenario demo berjalan, build bersih dari repository berhasil, dan berkas pengumpulan lengkap.
